## 2. Product model

### Customer and lead are different entities

A CRM customer represents one person. A lead represents one distinct inquiry or commercial opportunity belonging to that person.

- One customer can have many leads.
- The same inquiry can reopen the existing lead as a new cycle.
- A different inquiry creates a new lead.
- A customer is initially a `prospect`.
- A prospect becomes a real `customer` only after a confirmed paid LexGo purchase.
- Do not show a user-editable LexGo ID field. IDs are generated by the backend.
- A CRM customer can be linked automatically to an existing LexGo account by a verified phone number.

### Lead cycles

Every lead has a current cycle and can have historical cycles. Reopening a successful or rejected lead does not destroy its old result:

- the previous cycle remains immutable in history;
- its terminal status remains visible;
- the lead returns to `new` with a new cycle number;
- the new inquiry is appended separately;
- historical operator and conversion metrics remain correct.

Use `GET /crm/leads/{lead_id}/history` for the complete cycle and status history.

## 3. Authentication and common rules

Send the normal LexGo access token in the `Authorization` header exactly as used elsewhere in the application.

All write forms use backend validation. Render `detail.code`, `detail.field`, and related metadata from failed responses. Never infer permission from role names alone; use `permissions`, `scope`, `allowed_actions`, and other backend flags.

### Optimistic locking

Lead mutations require the current `lock_version` as `expected_lock_version` where the request schema requires it. After every successful mutation, replace the local lead object with the returned object and use its new `lock_version`.

If two users edit the same lead, the stale client must reload the lead instead of silently overwriting the other change.

### Raw JSON is not a UI

Lead and customer detail responses include `detail_sections`. Render these as titled sections with labels and values. Do not print `details` or arbitrary objects as raw JSON. `GET /crm/meta` returns `detail_rendering.raw_json_forbidden=true` as an explicit contract.

## 4. Bootstrap endpoint

Call `GET /crm/meta` when entering CRM and cache the response for the session.

It provides:

- fixed statuses and allowed transitions;
- score, language, contact and source options;
- current user's CRM permissions;
- data scope: `all` or `own_and_unassigned`;
- revenue visibility;
- telephony capabilities;
- customer/lead form metadata;
- Kanban URLs and realtime events;
- automation actions and no-answer SMS delay;
- detail rendering rules.

The frontend must build menus and buttons from these flags. A call-center operator must not see superadmin-only analytics, robot management, merge or live-call monitoring unless the corresponding permission is returned.

## 6. Kanban and lead list

### Fixed statuses

The six business statuses are:

1. `new`
2. `qualified`
3. `proposal`
4. `decision_pending`
5. `won`
6. `rejected`

Do not add `contacted`, `in_progress`, or similar columns.

### Kanban

`GET /crm/kanban?column_limit=30&q=&mine_only=false`

Response:

- `columns[]`: status definition, count, `has_more`, and lead items;
- `total`;
- `column_limit`;
- `fixed_statuses=true`;
- `reorder_supported=true`.

Lead cards can be reordered inside a status and moved between statuses. Submit status changes with:

`POST /crm/leads/{lead_id}/status`

```json
{
  "status": "qualified",
  "reason": "Customer need confirmed",
  "next_action_at": "2026-10-30T10:00:00+05:00",
  "expected_lock_version": 4
}
```

For `rejected`, a reason is required. `won` is not a visual-only status: the backend requires a linked order and confirmed payment.

### Status settings

`PUT /crm/kanban/columns` changes title, color and order, but all six keys are mandatory and cannot be removed.

This endpoint requires `crm.automation.manage`.

### Paginated list

`GET /crm/leads`

Supported filters:

- `status`, `score`, `source`, `region`, `q`;
- `assigned_operator_user_id`;
- `queue_only`, `mine_only`;
- `next_action_from`, `next_action_to`;
- `created_from`, `created_to`;
- `limit`, `offset`.

Response includes `items`, `total`, `limit`, `offset`, and `counts` by status.

## 7. Lead creation and duplicate behavior

Create a lead with `POST /crm/leads`.

The operator chooses either:

- an existing customer through `customer_id`; or
- a new customer through the nested `customer` object.

Do not expose `client_user_id` or `category` as normal form fields. Region comes from the selected customer by default. If the operator overrides the region in the lead, the backend updates the customer's latest region as well.

Important fields:

```json
{
  "customer_id": "customer-uuid",
  "source": "phone",
  "title": "Contract review request",
  "problem": "Customer inquiry text",
  "region": "Toshkent",
  "urgency": "normal",
  "preferred_language": "uz_latn",
  "details": {},
  "next_action_at": null,
  "assigned_operator_user_id": null,
  "force_create": false,
  "reuse_similar": true
}
```

When a similar inquiry is detected, the backend can reopen the existing lead rather than create a duplicate. To reopen manually:

`POST /crm/leads/{lead_id}/reopen`

```json
{
  "inquiry": "New inquiry text",
  "source": "phone",
  "reason": "Customer contacted LexGo again",
  "assigned_operator_user_id": null,
  "expected_lock_version": 6
}
```

For a confirmed duplicate use `POST /crm/leads/{lead_id}/duplicate-resolution` with `decision=duplicate`, `duplicate_of_lead_id`, and reason. For a false positive use `decision=not_duplicate`.

## 8. Customer select and customer modal

Use the paginated select endpoint, not a free-text UUID input:

`GET /crm/customers/select?q=&limit=30&offset=0`

Each item contains:

- name and public ID;
- primary phone;
- region;
- lead count;
- `is_lexgo_user` and a short LexGo badge label;
- `display_label` ready for a select row.

The lead form must support:

1. Existing customer: searchable paginated select.
2. New customer: open the customer creation modal above the lead modal.
3. After customer creation: close the customer modal, return to the lead modal, and automatically select the created customer.

Customer creation uses `POST /crm/customers`. The frontend must not show `user_id`; linking is automatic by verified phone.

Customer detail uses `GET /crm/customers/{customer_id}` and must show contacts, leads, orders, lifecycle, account-linking state, notes and `detail_sections`.

Contacts:

- `POST /crm/customers/{customer_id}/contacts`
- `PATCH /crm/customers/{customer_id}/contacts/{contact_id}`
- `DELETE /crm/customers/{customer_id}/contacts/{contact_id}` archives a contact.

The last active contact cannot be archived.

```json
  "operator_user_id": "user-uuid",
```

## 11. Watchers and collaboration

- Add: `POST /crm/leads/{lead_id}/watchers` with `{ "user_id": "..." }`
- Remove: `DELETE /crm/leads/{lead_id}/watchers/{watcher_user_id}`

Watchers receive realtime and normal notifications. Adding another user as watcher requires assignment permission; a user can manage their own watcher state.

## 12. Conversion to a LexGo order

`POST /crm/leads/{lead_id}/conversion`

The customer must already be linked to a LexGo account. Otherwise the backend returns:

```json
{
  "detail": {
    "code": "crm_customer_account_required"
  }
}
```

The operator can prepare service/package/seller/price/currency/note. The backend creates an `operator_draft` order with `unpaid` payment state. The customer must confirm and pay through the regular payment flow. Only a confirmed payment can convert the CRM customer lifecycle and allow `won`.

## 13. AI Copilot

Start a run:

`POST /crm/leads/{lead_id}/ai/runs`

Run types:

- `full_analysis`
- `summary`
- `qualification`
- `service_match`
- `draft_reply`
- `call_script`
- `follow_up`
- `offer`
- `live_call_assist`
- `post_call_summary`
- `sms_draft`

Request:

```json
{
  "run_type": "full_analysis",
  "language": "auto",
  "instruction": "Prepare the next best action"
}
```

The backend returns HTTP 202 with status `queued`. Observe completion through realtime notification `crm.ai.completed`, then fetch:

- `GET /crm/ai/runs/{run_id}`; or
- `GET /crm/leads/{lead_id}/ai/runs?limit=20`.

Possible statuses include `queued`, `running`, `completed`, and `failed`.

AI output can include summary, category, urgency, detected language, customer mood, agreements, objections, risks, missing information, questions, duplicates, service/specialist candidates, offer/reply/SMS drafts, call script, follow-up, suggested status, next action, confidence and operator warnings.

### Mandatory human approval

AI never changes data, sends messages, creates payment, or updates status automatically. The response contains `operator_confirmation_required=true` and `auto_executed=false`.

The operator selects individual output paths and may edit them before applying:

`POST /crm/ai/runs/{run_id}/apply`

```json
{
  "selected_paths": ["summary", "urgency", "next_action.at"],
  "overrides": {
    "urgency": "high"
  },
  "expected_lock_version": 8
}
```

Never provide an “Apply all silently” action.

If another AI run is already queued/running for the same operator and lead, backend returns HTTP 409 with `crm_ai_run_active` and the active `run_id`.

## 14. Calls and live transcript

Start/prep a call:

`POST /crm/leads/{lead_id}/calls`

```json
{
  "contact_id": "contact-uuid",
  "direction": "outbound",
  "purpose": "Clarify the legal issue"
}
```

The backend requires a phone contact and returns the provider/call state. Call recording requires an audible consent notice. The response includes the configured Uzbek consent text inside metadata.

List lead calls:

`GET /crm/leads/{lead_id}/calls`

Complete a call:

`POST /crm/calls/{call_id}/complete`

```json
{
  "status": "completed",
  "summary": "Call summary",
  "transcript": [],
  "recording_url": "",
  "metadata": {}
}
```

Allowed terminal statuses: `completed`, `no_answer`, `failed`, `cancelled`.

### Live transcript and operator assist

Append transcript segments:

`POST /crm/calls/{call_id}/transcript`

```json
{
  "segments": [
    {
      "speaker": "customer",
      "text": "...",
      "started_at_ms": 0,
      "ended_at_ms": 3200
    }
  ],
  "language": "auto",
  "request_ai_assist": true
}
```

The response returns `ai_run_id` when a new live-assist run was created. Do not create overlapping live-assist requests; the backend suppresses duplicate active runs.

### Supervisor Live Office view

Permission: `crm.live_calls.view`.

- `GET /crm/live-calls`
- `GET /crm/live-calls/{call_id}`

This view is read-only, audited, and shows the active call, transcript, lead/customer context and live AI suggestions. Every view is audit logged. Operators without this permission correctly receive 403.

## 15. SMS workflow

List: `GET /crm/leads/{lead_id}/sms`.

Create operator draft:

`POST /crm/leads/{lead_id}/sms`

```json
{
  "body": "SMS text",
  "language": "uz_latn",
  "contact_id": "phone-contact-uuid",
  "scheduled_at": null
}
```

Approve or edit and approve:

`POST /crm/sms/{sms_id}/approve`

```json
{
  "body": "Final operator-approved text"
}
```

SMS statuses can include:

- `draft`
- `scheduled`
- `approved`
- `sent`
- `delivered`
- `cancelled`
- `failed`
- `provider_configuration_required`

If a call ends with `no_answer`, the backend schedules the standard SMS after 180 seconds. If a later call is answered before sending, the SMS is cancelled automatically. Other AI SMS drafts always require operator approval.

Current operational note: show `provider_configuration_required` as “SMS provider is not configured” with a retry option after administrators configure the provider. Do not display it as delivered.

## 16. Automation robots

Permission: `crm.automation.manage`.

- List: `GET /crm/automation/rules?status=`
- Create: `POST /crm/automation/rules`
- Update: `PATCH /crm/automation/rules/{rule_id}`
- Dry run: `POST /crm/automation/rules/{rule_id}/dry-run`
- Run history: `GET /crm/automation/runs?status=&rule_id=&lead_id=&limit=&offset=`

Triggers:

- `lead_created`
- `status_changed`
- `lead_reopened`
- `call_no_answer`
- `call_completed`
- `next_action_due`
- `payment_confirmed`

Actions:

- `send_sms`
- `send_notification`
- `create_task`
- `change_status`
- `assign_owner`
- `add_tags`
- `escalate`

Conditions use `{field, operator, value}`. Supported operators are `eq` by default, `ne`, `in`, `not_in`, `contains`, and `exists`. Common context paths include:

- `lead.status`
- `lead.source`
- `lead.urgency`
- `lead.score`
- `lead.region`
- `lead.assigned_operator_user_id`
- `lead.cycle_number`
- `customer.lifecycle`
- `customer.language`
- `customer.region`

Rule statuses: `draft`, `active`, `paused`.

The dry-run endpoint returns matched context, proposed actions and `writes_performed=false`. Always provide dry-run before activation. Show run status, attempts, scheduled/start/completion timestamps, context, result and error. Backend uses idempotency and prevents the same rule from recursively triggering itself.

`POST /crm/exports`

```json
{
  "scope": "leads",
  "date_from": null,
  "date_to": null,
  "status": null,
  "source": null,
  "assigned_operator_user_id": null,
```

Flow:

1. POST returns HTTP 202 and job ID.

4. Handle `queued`, `running`, `ready`, `failed`, `expired`.

## 21. Realtime integration

Continue using the existing authenticated LexGo realtime connection and user channel. CRM notifications and updates are broadcast to `user:{user_id}`. Supervisors with permission also consume `crm:live-calls`.

Important events include:

- `crm.lead.created`
- `crm.lead.reopened`
- `crm.lead.claimed`
- `crm.lead.assigned`
- `crm.lead.transferred`
- `crm.lead.status_changed`
- `crm.lead.moved`
- `crm.kanban.columns_updated`
- `crm.lead.watcher_added`
- `crm.lead.next_action_due`
- `crm.lead.payment_confirmed`
- `crm.ai.completed`
- `crm.ai.failed`
- `crm.call.transcript_updated`
- `crm.call.completed`
- `crm.automation.notification`
- `crm.automation.escalated`
- `crm.export.ready`
- `notification.created`

Realtime handling rules:

1. Match events by `lead_id`, `customer_id`, `call_id`, or `run_id`.
2. Update lightweight badges immediately.
3. Refetch the authoritative lead after any mutation event instead of recomputing lock/version/status locally.
4. Move Kanban cards without a full page refresh, then reconcile with the API.
5. Sort queues by the latest backend state.
6. Show an animated top-right notification with click-through route when an actionable notification arrives.
7. Reconnect with backoff and refetch active views after reconnect because websocket delivery is not a historical event store.

## 23. Loading, empty and failure states

Every page must include:

- skeleton/loading state;
- empty state with a relevant action;
- retry state for network failures;
- permission-denied state without exposing hidden data;
- realtime reconnect indicator;
- background-job progress state;
- optimistic action disabled while the previous mutation is pending.

Do not clear existing data during a background refetch. Do not show a successful SMS, AI apply, export, order conversion or status transition before the backend confirms it.

## 25. Backend operational notes for frontend

- The deployed backend is the source of truth for permissions, status transitions, lifecycle, payment state and lock versions.
- Customer lifecycle changes only after real confirmed payment.
- A `won` lead cannot be produced by dragging a card without a paid order.
- AI always requires operator confirmation.
- Customer-private marketplace/advocate chats are not given to CRM AI.
- Live-call supervisor access is permission-protected and audited.
- SMS provider configuration is the only current external integration blocker; all application workflow and status handling are ready.
